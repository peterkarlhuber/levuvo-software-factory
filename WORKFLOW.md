# Levuvo SF Workflow

Status: draft v0.1.2 · 2026-11-21 · Part A specified, parts B and C planned

> This document specifies the intended behavior of the factory. During the concept phase, guards are requirements, not yet implemented or verified controls.

## Overview
- **A. New project (once):** A0 create project → A1 briefing → A2 interview → A3 PRD + feature list → A4 design → A5 skeleton
- **B. Feature (per feature, planned):** B1 spec interview → B2 spec (approval, Definition of Ready) → B3 planning + hidden scenarios → B4 test-first build + PR → B5 automated gates → B6 independent review → B7 docs + Definition of Done → B8 acceptance package → human authorizes merge → release version by SemVer compatibility impact
- **C. Bug (per bug, planned):** C1 report → C2 bug report → C3 classify (human decides) → C4 failing test + fix → C5 gates → C6 review → C7 docs + DoD → C8 acceptance package → human authorizes merge → release version by SemVer compatibility impact
- **Later:** backlog/prioritization, hotfix path, deployment/rollback/monitoring, process metrics.

Human decision points in part A: approve PRD + feature list (A3), product-relevant ADRs (A4), DoR/DoD (A5).

The playbook ([PLAYBOOK.md](PLAYBOOK.md)) holds the rules that apply everywhere. This document describes each workflow step: purpose, input, output, templates and the step-specific guards. Guard marks: [Enforced], [Verified], [Instructed] (see playbook).

## A. New project (once)



### A0 – Create project
The human creates a project in the factory and names it. The factory creates an almost empty repository on the local git server; everything else is created by the steps when needed.

- Initial content: `README.md` (project name + one line, generated). `briefing/` is created with the first A1 upload (git does not track empty folders).
- Added later: `docs/` with PRD, FEATURES, ARCHITECTURE, adr/, DESIGN-SYSTEM, DEPENDENCIES (A3/A4); `.devcontainer/` and code (A5); `features/<ID>/` for specs (B).
- Guards:
  - GA0.1 [Enforced] The repo is created private on the local Forgejo; the project name must be unique.
  - GA0.2 [Enforced] The factory bootstraps the repo itself and activates branch protection for `main` before any agent gets write access; no agent ever writes to `main` directly.
  - GA0.3 [Enforced] Optional GitHub mirror for archiving only; nothing runs there.

### A1 – Briefing
The human collects everything about the idea in the folder `briefing/`. Any files and any subfolders the human creates: notes, meeting notes, screenshots, images, PDFs, office documents, links. No predefined structure. The briefing may be rough and incomplete; A2 fills the gaps. Language: the human may write in any language; project artifacts are written in English.

- Input: anything the human uploads.
- Output: `briefing/` folder + briefing inventory.
- Templates:
  - `BRIEFING.md` – optional fill-in template (Idea, Problem, Users, Alternatives, Must-haves, Not wanted, Constraints, Examples, Attachments). No project name (the project already has one).
  - Briefing inventory (JSON, generated by the factory): every file with path, type, size, hash, readable by agents yes/no.
- Guards:
  - GA1.1 [Enforced] The briefing must not be empty: at least one file before A2 can start.
  - GA1.2 [Enforced] The factory generates the inventory itself; A2 records which inventory version it read.
  - GA1.3 [Enforced] Large files are stored via Git LFS.
  - GA1.4 [Verified] Uploaded files are scanned for credentials and secrets before agent access; detection is best-effort. [Enforced] Files with detected secrets are blocked until resolved.
  - GA1.5 [Enforced] Files agents cannot read (e.g. video) are marked in the inventory; A2 asks the human about them.

### A2 – Interview
An interview agent reads the whole briefing and clarifies only the gaps with the human. Goal: the product level (what and why) – it fills the PRD live, section by section, from the briefing and the answers. Not feature specs (B1/B2) and not tech/design (A4). This is an attended session: R2's "never wait in a chat" applies to unattended runs; the question format (one question, recommended answer) stays.

Flow: read all readable inventory files → draft every PRD section the briefing already answers (with source) → ask one question at a time with a recommended answer, updating the PRD live → as soon as the scope (PRD section 7) is drafted, derive the feature list live as well, and keep it in sync with later answers (each feature inside the scope; MoSCoW priority as a preliminary classification and dependencies, proposed by the agent, confirmed by the human; the actual work order is decided later) → end when every section is confirmed or listed under "Open questions" by the human.

- Templates: interview log (JSON: question, recommendation, answer, attachments, time). The PRD sections (A3) serve as the coverage checklist; each section has a status (open / drafted / confirmed) and a source.
- Guards:
  - GA2.1 [Enforced] The interview can finish only when every required PRD section is confirmed or explicitly deferred to Open questions by the human, and the initial feature list is non-empty. A merely drafted section is not sufficient.
  - GA2.2 [Enforced] The interview agent cannot write to the repo directly; it delivers PRD section drafts as structured output, the factory writes PRD and log.
  - GA2.3 [Enforced] The log records the inventory version read; any change to the briefing inventory (added, changed or deleted files) marks the interview as outdated. Exception: files the human attaches to an interview answer (G2.5) are added to the inventory and read at once; they do not mark the interview as outdated.
  - GA2.4 [Verified] Every drafted or confirmed section has a source (briefing file, human answer or attachment).

### A3 – PRD and feature list
The human reviews and approves the PRD (stable, changes rarely) and the initial feature list (living, changes often) together.

- Output: `docs/PRD.md`, `docs/FEATURES.md`.
- Templates:
  - PRD (common PRD sections, informed by the requirements-engineering principles of ISO/IEC/IEEE 29148:2018): 1 Vision, 2 Problem, 3 Users, 4 Alternatives, 5 Goals & success criteria, 6 Non-goals, 7 Scope (major capabilities and boundaries, no feature list), 8 Quality (performance, security, privacy e.g. GDPR, accessibility, languages, devices), 9 Constraints (hosting, budget, deadline, prescribed tech), 10 Open questions. Each section with status and source.
  - FEATURES.md (structured, rendered from JSON): ID, name, one sentence, priority (MoSCoW), depends on, status (set by the factory).
- Guards:
  - GA3.1 [Enforced] PRD approval requires all essential product decisions to be confirmed. Non-blocking open questions may remain only if the human explicitly accepts them as open.
  - GA3.2 [Enforced] The approved PRD is versioned with a hash; agents can only read it. Changes go through a PRD revision approved by the human.
  - GA3.3 [Enforced] Every feature gets a permanent ID that never changes or gets reused.
  - GA3.4 [Enforced] Every feature must fit the PRD scope; a feature outside the scope first needs a PRD revision. (The scope check itself is [Verified] by an agent, the block is enforced.)
  - GA3.5 [Enforced] Feature statuses are set only by the factory's state machine.

### A4 – Design
Based on the approved PRD, the basic technical decisions are made before the first feature is built. Attended session like A2: the agent proposes with a recommendation; the human decides only product-relevant points. Answers may carry attachments (G2.5), e.g. further design references.

Topics: 1 stack (language, framework, database, login, tests, hosting), 2 architecture (building blocks and how they interact), 3 data model, 4 design system (colors, fonts, spacing, components), 5 own dependencies (own repos: other factory projects or GitHub repos).

- Output / templates:
  - `docs/ARCHITECTURE.md` – lightweight arc42 documentation, with C4 System Context and Container diagrams where useful (components only if needed); includes the stack and a separate data-model description when applicable. Features later only add changes.
  - `docs/adr/NNNN-title.md` – MADR, one file per decision, marked "product-relevant" or "internal".
  - `docs/DESIGN-SYSTEM.md` + design tokens conforming to the Design Tokens Community Group (DTCG) Format Module 2025.10, where applicable.
  - `docs/DEPENDENCIES.json` – own dependencies: repo, purpose, pinned version, how it is integrated. Standard path: own libraries are published with SemVer versions to the Forgejo package registry (npm, PyPI, …) and consumed via the normal package manager; GitHub repos are mirrored to the local git server.
- Artifacts that do not apply to the project (e.g. no UI, no database, no own libraries) are marked as not applicable; they are not created as empty documents.
- Stack profiles: the factory supports a fixed list of stacks, each with its own image, gates and conventions (idea from Alex's stack packs).
- Guards:
  - GA4.1 [Enforced] The stack must match a factory stack profile; otherwise a new profile is needed first.
  - GA4.2 [Verified] Every ADR is "product-relevant" (hosting, login, cost, privacy, PRD constraints → human decides) or "internal" (agent decides).
  - GA4.3 [Enforced] Approved architecture, ADR and design-system baselines are versioned and cannot be modified directly by agents. Agents may propose updates through the factory. Significant architectural decisions require new or superseding ADRs; routine documentation and design-system updates do not. Product-relevant changes keep human approval.
  - GA4.4 [Verified] Every decision fits the PRD's quality requirements and constraints.
  - GA4.5 [Enforced] Own dependencies are always pinned to a fixed version.
  - GA4.6 [Enforced] Agents cannot modify the source of a separately managed dependency within the consuming project. Changes to the dependency itself belong to its own project.
  - GA4.7 [Enforced] Updating the consumed version is a separate change subject to all mandatory quality gates of the project's gate policy (R4).

### A5 – Skeleton
First unattended run. The agent builds a runnable, empty project from the design before any feature exists.

The skeleton goes through the normal approval path: feature branch, PR, mandatory gates, independent skeleton review (no hidden scenarios), acceptance package, human-authorized merge. Results are bound to the approved PRD and architecture baseline plus DoD/gate policy (there is no feature spec yet).

Flow: scaffold on a feature branch with the stack's official generator + one passing example test → describe the environment as a Dev Container (`.devcontainer/devcontainer.json`, open standard) → define commands install / dev / test / lint / build → the factory proposes DoR and DoD from the stack profile, the human approves → the factory generates the mandatory gates (R4) and Forgejo branch protection from them → the factory checks the skeleton in its own container.

- Templates: DoR and DoD (checklists with schema, gates are generated from them), `devcontainer.json` (Dev Container spec).
- Guards:
  - GA5.1 [Enforced] A5 is complete only after all mandatory gates are green in the factory container, the independent review and the Definition of Done passed, and the human-authorized merge succeeded.
  - GA5.2 [Enforced] DoR, DoD and gate policy live in the factory (R8); only the human can change them.
  - GA5.3 [Enforced] Branch protection and merge rights are set by the factory; agents have no merge rights (R3).
  - GA5.4 [Verified] The skeleton contains setup only, no feature logic.
